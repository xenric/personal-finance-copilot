# 개발 규칙

## 조사

- 수정 전에 관련 코드, 설정, 테스트를 확인한다.
- 기존 디렉터리 구조, 명명, 오류 처리 방식을 우선한다.
- 같은 역할의 기존 구현이 있는지 먼저 검색한다.
- 프로젝트의 실제 빌드·실행 명령을 확인하고 추정하지 않는다.
- 데이터 형식이나 저장 위치를 변경하기 전에 기존 파일과 호환성을 확인한다.

## 아키텍처

- 도메인 로직을 API, UI, 파일 저장소, 외부 서비스 코드와 분리한다.
- 재무 계산은 파일 입출력과 분리된 순수 로직으로 구현한다.
- 외부 API와 LLM SDK는 인터페이스 뒤에 격리한다.
- 도메인 계층이 파일 형식이나 외부 SDK에 직접 의존하지 않게 한다.
- 계층 간 순환 의존성을 만들지 않는다.
- 미래 확장만을 위한 추상화를 만들지 않는다.
- 실제 중복이 확인되기 전에는 공통화하지 않는다.
- 기존 아키텍처가 있다면 새로운 구조보다 기존 방식을 우선한다.

권장 의존 방향:

```text
UI / API
   ↓
Application
   ↓
Domain
   ↑
File Storage / External API / LLM
```

## 코드

- 함수와 클래스는 하나의 책임에 집중한다.
- 이름은 기술 구현보다 도메인 의미를 명확하게 표현한다.
- 숨겨진 부작용보다 명시적인 입력과 출력을 우선한다.
- 오류를 무시하거나 예외를 삼키지 않는다.
- 주석은 코드 동작보다 결정 이유를 설명한다.
- 사용하지 않는 코드나 설정을 추가하지 않는다.
- 관련 없는 포맷 변경이나 이름 변경을 섞지 않는다.
- 변경한 코드 주변의 기존 스타일을 따른다.

## API

- API 요청·응답 모델과 내부 도메인 모델을 분리한다.
- 입력값은 시스템 경계에서 검증한다.
- 필수값, 선택값, 기본값을 명시한다.
- 오류 응답 형식과 상태 코드를 일관되게 유지한다.
- 기존 API 계약을 불필요하게 변경하지 않는다.
- 금액, 통화, 비율, 날짜의 단위와 형식을 명확하게 한다.
- 내부 오류, 파일 경로, 민감정보를 외부 응답에 노출하지 않는다.

## 파일 저장 구조

데이터는 데이터베이스가 아닌 파일로 저장한다.

파일 저장 구현은 도메인 로직과 분리한다.

권장 구조:

```text
data/
├── profile/
│   └── financial-profile.json
├── current/
│   ├── assets.json
│   ├── liabilities.json
│   ├── holdings.json
│   └── cash-flow.json
├── snapshots/
│   └── YYYY-MM/
│       └── snapshot.json
└── reports/
    └── YYYY-MM/
        ├── review.json
        └── review.md
```

`holdings.json`은 투자상품 입력을 분리해 저장하기 위한 파일이다.
도메인 계산에서는 투자상품을 `Asset`으로 변환해 처리한다.

실제 개인 데이터가 저장되는 `data/` 디렉터리는 Git에 커밋하지 않는다.

저장소에는 다음 데이터만 둘 수 있다.

- 데이터 형식 예제
- 합성 테스트 데이터
- JSON Schema
- 빈 디렉터리 유지를 위한 파일

예제 데이터는 실제 데이터와 분리한다.

```text
examples/
fixtures/
src/test/resources/
```

## 파일 형식

구조화된 애플리케이션 데이터는 기본적으로 JSON을 사용한다.

- JSON: 프로필, 자산, 부채, 보유 종목, 현금흐름, 스냅샷, AI 보고서
- Markdown: 사용자가 읽는 재무 리뷰
- CSV: 데이터 가져오기와 내보내기
- YAML 또는 환경변수: 애플리케이션 설정

CSV를 내부 저장 형식으로 사용하지 않는다.

Markdown 보고서를 재무 계산의 원본 데이터로 사용하지 않는다.

각 영속 데이터 파일에는 가능한 한 다음 메타데이터를 포함한다.

```json
{
  "schemaVersion": 1,
  "createdAt": "2026-07-28T10:00:00+09:00",
  "updatedAt": "2026-07-28T10:00:00+09:00",
  "data": {}
}
```

## 파일 스키마

- 모든 저장 파일은 명시적인 스키마를 가져야 한다.
- 스키마 버전을 파일에 저장한다.
- 필드 추가 시 기존 파일을 읽을 수 있는 하위 호환 변경을 우선한다.
- 필드 삭제나 의미 변경은 명시적인 변환 절차를 제공한다.
- 알 수 없는 스키마 버전은 조용히 읽지 않고 오류로 처리한다.
- 파일을 읽은 직후 스키마와 필수값을 검증한다.
- 잘못된 파일을 기본값으로 덮어쓰지 않는다.

파일 구조 변경 시 다음을 검토한다.

- 기존 파일과의 호환성
- 변환 또는 마이그레이션 필요 여부
- 실패 시 복구 방법
- 이전 버전으로 돌아갈 수 있는지
- 테스트 fixture 수정 영향

## 파일 쓰기

파일 저장은 데이터 손상 가능성을 최소화해야 한다.

직접 대상 파일을 덮어쓰기보다 다음 순서를 우선한다.

1. 동일한 디렉터리에 임시 파일 생성
2. 전체 데이터 쓰기
3. 파일 내용 검증
4. 필요한 경우 디스크 동기화
5. 임시 파일을 대상 파일로 원자적 교체

쓰기 실패 시 기존 정상 파일을 보존한다.

부분적으로 작성된 파일을 정상 데이터로 취급하지 않는다.

여러 파일을 함께 변경해야 한다면 다음을 고려한다.

- 변경 순서
- 중간 실패 상태
- 재시도 가능 여부
- 롤백 또는 복구 방법
- 어느 파일이 최신 상태인지 판단하는 기준

## 파일 읽기

파일이 없는 경우와 파일이 손상된 경우를 구분한다.

- 파일 없음: 최초 실행 또는 데이터 미생성 상태
- 빈 파일: 잘못된 데이터 상태
- JSON 파싱 실패: 손상된 파일
- 스키마 불일치: 지원하지 않는 데이터 형식
- 필수값 누락: 유효성 검증 실패
- 권한 오류: 실행 환경 또는 설정 오류

손상된 파일을 임의로 초기화하거나 덮어쓰지 않는다.

오류에는 사용자가 복구할 수 있는 정보를 제공하되, 민감한 전체 데이터는 출력하지 않는다.

## 동시성

동일 파일에 대한 동시 쓰기 가능성을 검토한다.

초기 MVP에서는 다음 정책을 우선한다.

- 단일 애플리케이션 인스턴스
- 프로세스 내부 쓰기 직렬화
- 하나의 파일에 동시에 두 번 쓰지 않기
- 저장 중 중복 요청 방지

동시 실행을 지원해야 한다면 파일 잠금 또는 버전 검사를 추가한다.

파일 잠금 없이 여러 프로세스가 같은 데이터 디렉터리를 수정하도록 만들지 않는다.

## 파일 경로

- 데이터 루트 경로는 설정으로 관리한다.
- 소스 코드에 사용자별 절대 경로를 하드코딩하지 않는다.
- 경로를 결합할 때 운영체제 독립적인 API를 사용한다.
- 사용자 입력을 그대로 파일 경로로 사용하지 않는다.
- `..` 등을 이용한 상위 디렉터리 접근을 차단한다.
- 심볼릭 링크와 경로 탈출 가능성을 검토한다.
- 파일명에는 안정적인 식별자와 표준화된 날짜 형식을 사용한다.

날짜 기반 파일명은 다음 형식을 우선한다.

```text
YYYY-MM
YYYY-MM-DD
```

지역화된 날짜 문자열을 파일명이나 식별자로 사용하지 않는다.

## 백업 및 복구

개인 재무 데이터는 복구 가능해야 한다.

- 중요한 파일을 덮어쓰기 전에 백업 가능성을 고려한다.
- 백업 파일에는 생성 시점이나 버전을 표시한다.
- 백업 개수와 보존 기간을 제한한다.
- 사용자가 데이터 전체를 내보낼 수 있는 구조를 유지한다.
- 손상된 파일을 발견하면 정상 백업으로 복구할 수 있게 설계한다.
- 복구 기능은 원본 파일을 즉시 삭제하지 않는다.

초기 MVP에서는 최소한 다음을 지원한다.

- 수동 데이터 디렉터리 백업
- JSON 전체 내보내기
- 기존 스냅샷 불변 보존

## 스냅샷

스냅샷은 생성된 시점의 재무 상태를 보존한다.

- 생성된 스냅샷을 현재 데이터 변경에 따라 수정하지 않는다.
- 같은 기간의 스냅샷을 덮어쓸지 새 버전을 만들지 명확하게 정한다.
- 스냅샷에는 계산 기준일과 스키마 버전을 기록한다.
- 당시 사용한 가격, 환율, 규칙 버전을 추적할 수 있게 한다.
- 과거 스냅샷을 읽지 못하는 변경은 피한다.

기본 정책은 스냅샷을 불변 데이터로 다루는 것이다.

## 설정

- 환경별 차이는 설정 또는 환경변수로 관리한다.
- 데이터 저장 경로는 설정 가능해야 한다.
- API 키와 비밀값을 소스 코드에 저장하지 않는다.
- 설정값은 시작 시점에 검증한다.
- 잘못된 필수 설정은 빠르게 실패시킨다.
- 비즈니스 임계값을 여러 코드 위치에 하드코딩하지 않는다.
- 설정 추가 시 기본값, 필수 여부, 사용 위치를 문서화한다.
- 로컬 설정과 개인 데이터 파일은 `.gitignore`에 포함한다.

## 의존성

새로운 라이브러리를 추가하기 전에 다음을 확인한다.

- 표준 라이브러리나 기존 의존성으로 해결 가능한가?
- 단순 JSON 읽기·쓰기에 과도한 의존성을 추가하는가?
- 유지보수 상태와 라이선스가 적절한가?
- 보안 및 빌드 크기에 미치는 영향은 무엇인가?
- 테스트에서 쉽게 대체할 수 있는가?

의존성을 추가하면 이유와 사용 범위를 보고한다.

## 테스트

파일 저장 기능에는 가능한 한 다음 테스트를 포함한다.

- 정상 파일 읽기와 쓰기
- 파일이 없는 최초 실행
- 빈 파일
- 손상된 JSON
- 지원하지 않는 스키마 버전
- 필수값 누락
- 임시 파일 쓰기 실패
- 대상 파일 교체 실패
- 기존 파일 보존 여부
- 경로 탈출 시도
- 동시에 발생한 쓰기 요청
- 이전 스키마 데이터 호환성

테스트에서는 실제 개인 데이터를 사용하지 않는다.

각 테스트는 격리된 임시 디렉터리를 사용하고 실행 후 정리한다.

## 완료 전 확인

- 도메인 로직이 파일 입출력과 분리되어 있는가?
- 저장 파일에 스키마 버전이 있는가?
- 파일 쓰기가 원자적으로 처리되는가?
- 쓰기 실패 시 기존 파일이 보존되는가?
- 손상된 파일을 조용히 덮어쓰지 않는가?
- 개인 데이터 경로가 Git에서 제외되어 있는가?
- 파일 경로가 사용자 입력에 의해 탈출할 수 없는가?
- 스냅샷이 과거 상태를 그대로 보존하는가?
- 관련 파일 저장 테스트가 포함되어 있는가?
